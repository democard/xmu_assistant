# 签到进度与状态修复交接

日期：2026-09-20。基线：`7e1a894`（已发布 v1.7.0）；工作分支：`fix/attendance-leave-progress`。

## 已确认的真实故障

用户同时在 Android 进行中签到、Windows 历史记录中遇到人数进度未获取。经用户授权，仅复用本机已有登录会话，读取截图中一条异常记录的 `student_rollcalls` 明细。

- 总计 3 次 GET：旧磁盘会话的前 2 次返回 302，均未跟随跳转；用户自行重新登录后，第 3 次返回 200。
- 没有自动登录、没有提交签到、没有重试循环，没有继续读取其他课堂记录。
- 成功响应的顶层名单共 73 人：72 条 `status=on_call` / `rollcall_status=on_call_fine`，1 条 `status=on_leave` / `rollcall_status=on_personal_leave`。
- 旧解析器把请假归为 unknown，因此整个名单被判为不可靠。这次故障的根因是状态词表不完整，既不是未取得名单，也不是二维码/数字码读取问题。
- 正确结果为已签 72 / 名单总人数 73，比例约 98.6%。请假保留在分母中，不计作已签或缺勤。

只保留脱敏状态样例；仓库不包含名单身份、Cookie、密码、真实签到码或完整原始响应。该结果能证明这一条 Windows 记录的原因，以及 Android 相同解析代码存在同一缺陷；未读取用户当时那一条 Android 进行中签到，不能断言所有“未获取”都来自同一原因。

## 状态口径与证据

| 接口值 | 统计归类 | 依据 |
| --- | --- | --- |
| `on_call`、`on_call_fine` | 已到场/已签 | 本次实际响应、既有参考代码 |
| `on_leave`、`on_personal_leave` | 请假 | 本次实际响应 |
| `late`、`on_call_arrive_late` | 迟到，计入总人数，不计已签 | 下列 FJU 项目的字段映射；用户明确要求迟到不计已签 |
| `on_sick_leave`、`on_public_leave` | 请假 | 下列 FJU 项目的请假处理 |
| `absent` | 缺勤/未到场 | 既有接口契约 |

- [TronClass 官方教师指南](https://support.tronclass.com/quickguidance_teacher/WGTCQuickGuidance%28teachers%29.pdf)列出迟到、早退、迟到兼早退及多个假别，不能把界面看见的所有状态压成已签/缺勤二选一。
- [FJU 状态定义，固定提交](https://github.com/FJU-Devs/fju-aio/blob/034e54bf44cfeaf1bb519cdea78f6c128579028a/fju-aio/Models/RollcallModels.swift#L28)：迟到有精确字段映射；该项目将 `late` 视为已经完成签到。仅作为同平台兼容性证据，不宣称这些状态全部在厦大本次响应中出现。
- 早退和其余假别尚未取得可确认的厦大接口枚举，不凭英文猜字段，不使用 `on_call_*` / `*_leave` 的宽泛前缀或后缀匹配。
- 用户进一步明确：这里需要的是**明确已签人数**，不是已到场人数。迟到、请假、缺勤都不计已签。此前把迟到计入 `present` 的统计口径已纠正；个人状态和自动提交保护不由这个统计数反推。

### 最终统计规则（以此节为准）

每一行优先读取 `rollcall_status`，其次 `student_rollcall_status`，最后兼容仅有 `status` 的旧响应。首个非空有效状态只有精确 `on_call_fine` 或 `on_call` 才算已签。比如 `status=on_call` 配合 `rollcall_status=on_call_arrive_late`，详细状态为迟到，不能算已签。

其他非空状态，包括尚未列出的新假别或考勤类型，都只进入分母，不能因词表未覆盖而隐藏全班比例。`unknown` 分项可以保留其他类型计数，但不能再作为比例不可用的条件。真正缺失/空名单、损坏结构、状态字段缺失、重复名单或明确的部分名单仍需要区分处理。

例如 70 人已签、2 人迟到、1 人请假、2 人缺勤，应为 **70/75 = 93.3%**，而非 72/75。原有 72 人已签、1 人请假的实测记录仍为 72/73。

## 修复原则

1. 双端保留已签、缺勤、请假、迟到、其他状态分项，保持旧构造调用兼容；分项之和等于名单总人数。
2. 全班统计按详细状态优先，只计明确已签；不要求名单中的每一种状态都先被识别。个人判定仍使用独立的严格规则，不与全班计数混用。
3. 本人已请假不应触发首次自动签到；本人已到场（含迟到）不应重复自动提交。请假不伪装成本人已签或明确缺勤。
4. 名单读取失败或结构不完整仍不给有效比例；正常非已签状态不再使门槛永远无法满足。历史页面的显示回退不能进入自动控制流程。
5. Android 进度缓存保留请假、迟到计数，校验计入全部分项；升级缓存语义版本，防止旧缓存继续把迟到算成已签。
6. Android 支持类型的提交失败不得记入成功/完成集合；有界恢复和回执不明后的本人核实守卫仍然保留。

## 同类问题复查

- 确认并修正了“本人已请假但首次门禁仍可提交”：原布尔本人状态不能表达请假，不能仅靠 `own_present != True` 决定仍需提交。
- 确认并修正了 Android 雷达签到返回 False 后仍进入完成集合的分支。False 与成功分开，达到尝试上限后停止写入，不能用健康成功回调掩盖失败。
- 本人行中的 `on_call` 与 `on_call_arrive_late` 属同一个已到场大类；应保留迟到细类，不能被多字段一致性检查误伤。
- 多字段或多个本人候选行明确冲突时，不取第一个值直接认定已签。本人记录存在但无法确定时，不再用活动聚合状态补成个人结论。
- 自动门禁区分“没有本人明细”与“本人明细明确存在歧义”：前者可使用当前用户活动行的明确终态防重复，后者暂停一轮、不提交、不记完成，下一轮确认未签后可恢复。旧列表的已签不能覆盖明确的本人缺勤或状态冲突。
- Windows 统计补齐明确的 `is_current_user` / `is_self` 布尔标记，避免登录名与名单学号不同而漏识别本人；多个候选相互冲突仍不下结论。
- 已核对停止监控、换号、设置变更的提交前守卫及按账号回写 Cookie 的逻辑；本轮未复现串号提交。不把已经发出的网络请求能够被即时撤回来作为承诺。
